# Offline work in Mark Robot modules

PostgreSQL owns posted records, balances, inventory, salaries, attachments and receipts. During a verified session, a person may reopen a previously viewed page offline or prepare a supported command. A queued purchase, outgoing message or expense stays pending until the server validates the original request and returns a receipt. Local copies show their source and timestamp. A query that the device has never saved reports `OFFLINE_NOT_CACHED`.

## Authenticated scope

The registry requires the existing local account service and cloud identity. In local mode a configured device must have its verified local owner. In employee mode the active local and cloud account IDs must match. Account status, expiry, permissions, workspace, backend endpoint and both account session versions participate in authorization. A local grant or cloud authentication generation change invalidates a mounted view immediately, including asynchronous file work. The cloud client also enforces the verified local identity on every authenticated call, token renewal and result. A local owner switch, sign-out or verification failure clears the live bearer and refresh continuation before the account UI reloads. The owner continuation is bound to the app mode, cloud account, tenant, server epoch, and verified local owner and epoch. The employee URL clears this tab’s copied owner continuations and requires an explicit employee login. Employee sessions remain in memory. Existing unscoped cloud continuations require one fresh sign-in on upgrade. The optional cloud request guard checks the local permission again after token renewal and before delivering a result.

A server denial purges the bound projections and downloaded blobs and quarantines unsynchronized instructions. A fresh login or later permission verification can rebind the device. No command is automatically replayed across a changed grant or a quarantined binding. Each authorized person can inspect their own saved drafts in **Sync**. Recovering a quarantined draft requires a current server permission check, including the source and destination membership for chat. An explicit discard removes a reviewed rejected or quarantined instruction. Unrelated accounts do not see that draft.

### Cold offline owner access

A deployed server can issue a P-256 ES256 grant for a configured, verified local owner who is also the authenticated cloud owner. With a valid grant, an offline reload or a new tab can show saved Gallery, Chat, My Files, Finance, Payroll and Metals pages, and prepare the same safe queued commands. The native shell labels the session **Saved copies**, gives its last verified and expiry time, and exposes `authenticated:false, offlineVerified:true`. Assistant and server administration stay live-only. Reconnecting the network alone cannot send a command. A freshly authenticated cloud session must match the same tenant, owner, epochs and effective permissions to replay it.

The server signs the allowed app origin, issuing endpoint, workspace, cloud owner and session epoch, effective permission catalog hash, local owner ID, epoch and device-local retirement marker, device public-key thumbprint, issuance, purpose and expiration. It obtains the cloud owner and workspace from the authenticated server session. Local identity and nonextractable device-key possession are verified independently on the device. The browser checks the ES256 signature against the public key obtained via the authenticated HTTPS response and the public thumbprint pinned in the deployed shell. Every cold restore requires a new proof with that device’s nonextractable private key and a current verified local owner continuation or password session. The account switch retires the signed marker synchronously before navigation, including when browser quota prevents saving a replacement. A copied role hint, another employee, a remote-mode employee, another browser device, or an unconfigured local owner cannot open the projection.

The grant is valid for at most 24 hours, further bounded by the cloud account’s expiry. Local account expiry, observed clock rollback, role/epoch changes, signed-out state, and observed server denials lock or invalidate saved access. A disconnected device learns remote changes when it next contacts the server. Owner-grant expiry seals the UI; original pending instructions remain recoverable after the correct owner signs in. Closure of all tabs stops foreground processing. Actual cached content and pending work still depend on the browser retaining site data.

The operator provisions a separate key outside the repository before enabling cold owner access. Run `node supabase/management/generate-offline-owner-key.mjs /absolute/private/path/owner-signing.jwk` in a private operator context. The helper creates a new mode-0600 file without overwriting and displays only its public RFC 7638 thumbprint. Set the file’s contents as the Edge secret `WOW_OFFLINE_OWNER_SIGNING_JWK` through the normal secret manager, and set the public `offlineGrantPin` value in the deployed cloud configuration to the displayed thumbprint. Configure the exact HTTPS app origin in `WOW_ALLOWED_ORIGINS`. Rotating the public pin invalidates grants signed by the old key once the updated shell is installed. A previously installed shell that stays offline enforces its signed deadline. A missing or mismatched key/pin leaves cold offline access disabled and the shell asks the owner to verify online. Existing authenticated tabs retain ordinary in-session offline support. The signing key and a valid production grant are never shipped in source.

The grant is a purpose-specific saved-copy authorization. Cloud authentication, API authorization, account timeouts and every server posting still use the normal cloud session. Its signature and key thumbprint follow [RFC 7518](https://www.rfc-editor.org/rfc/rfc7518) and [RFC 7638](https://www.rfc-editor.org/rfc/rfc7638).

## Cached projections and commands

| Section | Saved reads | Durable writes | Requires a live connection |
| --- | --- | --- | --- |
| Gallery | Catalog/studio pages, own/staff order pages, personal orders, individual product sales | Versioned stock, order updates, preferences, presentation, quoted checkout, sale, sale reversal | Image handles and uploads, changed-command review |
| Chat | Self profile, rooms, feed pages by room/filter/cursor, members by room | Send, forward, send with attachment | Directory lookup, signed asset handles, standalone uploads, group/member administration, typing, reading, reactions, edits |
| My Files | File pages by folder, search, sort, archive state, kind and offset. A deliberate authorized download may save a verified blob | File upload with immutable request ID and bytes | Private open/share URLs and metadata changes |
| Finance | Finance, payroll and metals list pages by tenant, grants, tab, pagination and filters | Finance resource, transaction, transfer, manual quote, reversal. Payroll employee, attendance, removal, payment, reversal. Metals trade, manual quote, reversal | Attachments, archive/restore and live market capture |
| Assistant and server administration | No private page persistence | No queued actions | Every request |

Unexpired cache-first intervals are 4.5 seconds for chat rooms/feed, 10 seconds for members, 15 seconds for orders and financial pages, 20 seconds for files, 30 seconds for catalog/studio and 60 seconds for the self profile. A deliberate refresh bypasses the interval. Identical concurrent reads in the same mounted view share one request. A successful command invalidates the corresponding page family. All finance sections share this invalidation because a payroll posting can change a cash balance.

Rooms, feeds and file lists send the previous authorized projection’s hash state to the server. It evaluates row visibility and sends changed rows, deletions and any changed ordering or summary. The client reconstructs the complete page. A rejected or mismatched baseline triggers one full read. The transport also accepts bounded deltas for other actions whose server handlers supply them. Other reads return bounded complete pages. The outbox sends each individual command, never a full database snapshot.

Expired/disappearing messages, disappearing previews or quoted text, and live typing indicators are omitted from device copies. A refreshed complete room list removes cached pages for lost memberships and holds affected pending instructions. Downloaded bytes must match the SHA-256 in a fresh, explicit download authorization. The format, name, scope and file metadata version are checked before storage. Signed URLs and application credentials are excluded from storage. The service worker precaches shell assets only for these modules. It cannot send private API traffic with a logged-in person’s credentials.

## Device storage and scheduling

The browser uses the origin’s IndexedDB database `MarkRobotPrivateModules_v1`, schema version 2. The additive upgrade from version 1 adds owner-grant/device state in place and retains pending commands and payloads. One transaction atomically binds the identity, enqueues a command and its payload, claims a lease, or settles a server receipt. Strict transaction durability is requested when supported.

| Object store | Contents |
| --- | --- |
| `bindings` | Principal, session/grant scope, rotating binding seal, last verified time, next command ordinal, page invalidation versions and active-room roster |
| `grantState` | Device proof key, authenticated public signing key and the signed scope-bound offline owner grant. Revocation removes the grant in the same transaction as freezing the binding |
| `cache` / `content` | Compact projection and blob size/access metadata, separate from authorized page data or bytes |
| `jobs` / `payload` | Immutable command fingerprint, original UUID, owner, required permissions, FIFO position, attempt/lease metadata and receipt, separate from command fields and raw upload blob |

The global clean cache uses the smaller of 32 MiB and 2% of the browser quota estimate, with 180 entries maximum. One page may use up to 1 MiB and one requested file up to 8 MiB. The queue uses the smaller of 32 MiB and 4% of quota, with 160 outstanding instructions maximum. A command record is limited to 12 MiB, and uploaded bytes to 8 MiB. Quarantined, failed and conflicted work counts against the same limit. At most 100 compact posted receipts are retained, with a seven-day retention check during writes. Browser-driven eviction can still remove an entire origin.

Size limits apply across accounts on the device. Least-recently-used clean entries can be removed to fit a new page or explicit file. On a real browser quota error the transport can free the same principal’s clean copies and retry once. It never silently removes an unposted instruction to recover space. If an atomic enqueue cannot commit, the operation reports a storage error and no network command starts. The panel exposes the browser’s persistence result; only its explicit user action calls `navigator.storage.persist()`.

A transactional 60-second lease coordinates writers across tabs. The original payload digest and command/request UUID survive a crash or lost acknowledgement. A later lease holder can retry that same command. The server’s idempotent receipt prevents a second posting, and a superseded lease cannot overwrite the winning receipt. Transient failures back off with jitter starting around 1.5 seconds and capped around five minutes. New tabs and repeated manual clicks respect the stored retry time. Terminal conflicts retain the original draft for review. Sync runs on authenticated startup, reconnection, returning to a visible tab, a queue notification or manual request. Idle and hidden tabs do not poll the server. Browsers can suspend or terminate a closed app. Catch-up resumes on a later authorized visible session.

The production client uses native IndexedDB, Blob, Web Crypto and optional BroadcastChannel. There is no production database package, worker runtime, AI model or persistent polling loop for this feature. Upload fallback conversion yields between bounded slices. Binary content is kept out of metadata scans. The test-only IndexedDB implementation is pinned in the development lockfile.

## Module interface

- `request(action, payload, {refresh:true})` forces a read. Cached reads return the ordinary complete body and `_sync: {source, stale, cachedAt}`. A deferred write returns `{queued:true, queueId, commandId}` or its `requestId` equivalent. A successful immediate write returns the server receipt.
- `getConnection()`, `subscribeConnection(fn)` and `syncNow()` expose connection, pending, rejected and access-change state. The returned unsubscribe function releases each subscription.
- `subscribeReceipts(fn)` emits `{queueId, action, commandId|requestId, status, result, errorCode?}`, with status `posted`, `conflict` or `failed`.
- `listOutbox()`, `getDraft(queueId)` and `discardDraft(queueId)` operate inside the authenticated route and its current capabilities. The status panel can save a user-requested private copy of a draft or its attachment.
- `localFiles.get(fileId)` returns a matching private entry or null. `localFiles.put(fileId,{blob,fileName,contentType,digest})` requires the short-lived in-memory proof from a successful `files.open` request with `download:true`.

## Verification

Run `node --test tests/offline-platform* tests/wow-cloud-client.test.cjs`. The suite executes the production storage adapter against stateful IndexedDB, the real registry guards, a controlled token-renewal race, the ES256 grant issuer/verifier with a fresh offline app instance, and a production Edge file-upload handler against embedded PostgreSQL. It checks lost acknowledgements, simultaneous tabs, changed grants, cache scope, SHA-256, quota rollback, hidden-tab suspension, dirty forms and delta recovery. Browser storage persistence, OS-level eviction and completion while the app is closed are browser/device behaviors. The automated suite does not simulate a native browser rendering session.

Browser storage permissions, estimates and storage-pressure behavior are described by the [WHATWG Storage Standard](https://storage.spec.whatwg.org/) and [MDN’s quota and eviction guide](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria). Background Sync availability is documented in the [MDN Background Synchronization API reference](https://developer.mozilla.org/en-US/docs/Web/API/Background_Synchronization_API).
