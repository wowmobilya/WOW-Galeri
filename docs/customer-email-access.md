# Customer email access

This implementation belongs to the permanent Mark Robot service for WOW FURNITURE. It has not been deployed to the paid project, and no message has been sent to a real mailbox during local verification.

## Registration and recovery

Customer registration first requests proof of mailbox ownership. The visitor supplies a display name, username, company, email, country, international calling code and national phone number. The public request cannot choose a role or permissions, and it cannot set a password. Supabase Auth generates and sends the email proof. The mailbox holder chooses a password only after opening the proof link. This avoids giving the signup initiator a password that remains valid after someone else confirms an address.

Each outgoing email receives an independent 256-bit random challenge generated by Edge. Only its SHA-256 hash is stored with the private request. The raw challenge appears only in the callback fragment delivered through Auth's email template; it is never returned in the public request acknowledgement or saved to browser storage. PostgreSQL checks the challenge before Auth consumes the proof, and checks it again when claiming the password operation. Two requests for the same mailbox, even in two enabled workspaces or two permitted origins, cannot exchange their email links.

The Edge service verifies the one-time proof with Auth, calls `getUser`, and compares the verified identity and email against the private request. PostgreSQL checks that the Auth user and session still exist, the email is confirmed, the workspace is active, the request belongs to that workspace and application origin, and registration is enabled. It then creates a `customer` account with exactly `gallery.view`, `myorders.view`, `myorders.edit`, `chat.view`, `chat.edit`, `files.view`, and `files.edit`. No existing account is reclassified. The normal username and password login opens the application session after verification finishes.

Recovery is restricted to active customer accounts registered through this workflow with a stored customer profile and verified real email. Existing owner and staff accounts, including accounts provisioned under `@wow.invalid`, retain their current password-management workflow. Recovery does not turn a suspended account back on. The SQL claim invalidates application sessions before requesting the external password change, and completion invalidates them again. A provider error or lost response can make the password-change result uncertain; the UI directs the person to try the new password or request a fresh link. It never reports a successful password change without a successful final receipt.

The customer identity boundary is permanent: an account backed by `wow_customer.profiles` remains a `customer`. A private database trigger rejects promotion to owner, staff or a custom role through either the application or Dashboard edits, including while an Auth password update is in flight. To give that person staff or owner access, the owner provisions a separate managed login. Existing unrelated managed accounts retain their role-management workflow. Account suspension, deletion, expiry and permission revocation remain available; recovery cannot undo them.

Email verification and recovery sessions stay inside the Edge invocation. They are not returned to the browser or saved to IndexedDB, localStorage or sessionStorage. A valid proof that fails mailbox or request eligibility closes only its newly created Auth session, preserving that person's unrelated existing sessions. Global Auth logout is attempted only after a bound eligible recovery claim or successful registration; application session versions provide the independent revocation check. Public handlers never grant a normal application session based on user-editable Auth metadata.

The confirmed email is verified identity information. Phone, country, name and company are supplied by the customer; the phone is not SMS-verified. Country selection supports the 249 ISO country codes with localized, searchable names; the server checks the country code, international prefix, numeric national number and the 15-digit E.164 length ceiling. National numbering-plan rules are not inferred from the country field.

## Server and owner opt-in

The feature remains disabled unless both the server flag and the owner's workspace setting are enabled. The owner can independently allow new registrations and recovery. The control panel displays provider-accepted requests, failed requests and completed verifications over the last 24 hours. Provider acceptance is not proof of delivery to a mailbox.

Assembly contract:

```js
import {createCustomerAuthProvider,createCustomerAuthActions}
  from './modules/customer-auth.mjs';

const customerProvider=createCustomerAuthProvider({
  url:Deno.env.get('SUPABASE_URL'),
  serviceKey:secretKeys.default||Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')
});
const customerAuth=createCustomerAuthActions({
  provider:customerProvider,auth:remote.auth,origins,
  enabled:Deno.env.get('WOW_CUSTOMER_AUTH_ENABLED')==='true'
});
// Merge customerAuth.actions into authenticated moduleActions.
// Pass customerAuth.publicActions as createHandler's publicActions.
```

Apply `supabase/modules/customer-auth.sql` after the foundation. It adds a private `wow_customer` schema and the service-only `wow_customer_auth_service(text,jsonb)` wrapper. Its helper `wow_customer.contact(uuid)` is reserved for an already authorized internal communications service; the service must first verify workspace and order access. It returns active customer contact information only when the current Auth email is confirmed and matches the stored login email.

Load `modules/customer-auth/workspace.js?v=1` early in the document, before other scripts or external resources, and load `styles.css?v=1`. The script captures a proof from the URL fragment and removes proof parameters from the visible address before the application boots. The existing remote account card mounts the visitor form. Local owner login is unaffected. The control panel can mount `WFCustomerAuth.mountOwner({container,api,lang})` inside the existing owner server page and dispose it on account change.

The activated public cloud config must contain the actual workspace ID for visitor links that omit a `workspace` query parameter. Public registration has no implicit multi-workspace fallback. Keep the server allowlist limited to the verified production application origins.

## Supabase email setup and hosted acceptance

Supabase's current [email template documentation](https://supabase.com/docs/guides/auth/auth-email-templates), [email verification documentation](https://supabase.com/docs/guides/auth/auth-email-passwordless), [recovery reference](https://supabase.com/docs/reference/javascript/auth-resetpasswordforemail), and [official Auth client implementation](https://github.com/supabase/supabase-js/blob/master/packages/core/auth-js/src/GoTrueClient.ts) were checked for the provider contract. The native REST adapter uses `/otp`, `/recover`, `/verify`, `/user`, and `/logout`, with the server credential confined to Edge environment variables.

Before enabling public registration on the target project:

1. Verify the actual SMTP provider, sender domain, account credentials and provider limits in the authorized account. Use a company sender identity that the provider permits. Do not put SMTP credentials into a browser file.
2. Set Supabase Auth's Site URL and redirect allowlist to the actual application origins and required root callback patterns. The Edge service builds the callback itself from its origin allowlist; it ignores request-supplied redirect URLs. A request includes a workspace UUID, a request UUID, `wf-cloud=employee`, and `wf-customer=register` or `recover`. The generated `RedirectTo` already ends with `#challenge=<random-per-message-value>`.
3. Configure **Confirm signup**, **Magic link**, and **Reset password** templates with the following confirmation link. The first-time OTP flow can use the signup template; later OTP requests use the magic-link template.

```html
<p>WOW FURNITURE · مارك ربوت</p>
<p><a href="{{ .RedirectTo }}&token_hash={{ .TokenHash }}">Continue securely / متابعة آمنة</a></p>
<p>If you did not request this email, ignore it.</p>
```

4. Keep email proof expiry at one hour or less, matching the application's one-hour request lifetime. Supabase also rejects expired or reused proofs. Opening the page does not consume the proof; the user must enter and submit a new password. Tokens in URL fragments are not transmitted to static hosting as request parameters.
5. If Auth's CAPTCHA setting is enabled, integrate the selected provider through `WOWAuthCaptcha.execute(flow)`, which returns its token for this explicit form submission. No CAPTCHA provider is silently selected or remotely loaded by this module. The server passes an optional token to Auth; all application rate limits also apply without CAPTCHA.
6. Enable `WOW_CUSTOMER_AUTH_ENABLED`, then enable the workspace settings from the owner panel. Use an authorized test mailbox to complete signup, normal sign-in and recovery. Check the actual email link origin and the final username/password flow; an HTTP 200 for the request alone is insufficient.
7. Verify old and reused links, an expired request, a second unauthorized account, changed account status, and sign-in from a second device after recovery. Record the observed mailbox result and deployed commit before opening registration to all customers.

The `&token_hash=` suffix appends the Auth token to the existing challenge fragment. Do not replace it with a second `#` or drop the existing fragment: either change breaks request binding and the application rejects the link. Hosted acceptance must inspect a real received link and confirm both fragment fields survived the template and redirect allowlist. Old unbound pending requests are marked aborted by the upgrade; those users request a fresh email.

The shipped email templates should retain the fragment link. A query-form token is defensively stripped if encountered, but it can already have reached hosting logs before JavaScript runs. The challenge must be in the fragment; a query-only challenge is rejected. No new flow should generate query-form proof links.

## Bounds and maintenance

The service allows at most 90 public email requests per workspace per hour, at most three requests per normalized email per hour, and at most 12 verification attempts per request. A workspace-wide verification bucket is bounded at 120 attempts per 15 minutes. Counters are private and commit rejected attempts. Known, unknown and ineligible email addresses receive the same public request acknowledgement. Error detail from a provider is not sent to the visitor. An acknowledgement means the request was handled, not that a person received a message.

The private SQL job `wow-customer-auth-prune` runs at `17 * * * *`. Each run removes at most 500 requests that expired more than seven days ago and at most 500 rate-counter rows older than two days. Registration and the owner status endpoint also run the same bounded pruning helper. No browser needs to be open. The job does not delete provider Auth users or company accounts. Provider-side Auth records and audit retention remain governed by the project's Auth administration and retention settings.

## Local verification

`tests/customer-auth.test.mjs` runs the actual Edge dispatcher, native provider adapter, customer SQL and browser identity client against PostgreSQL fixtures for provider-owned Auth and Cron. It checks registration ordering, customer-only permissions, private contact fields, owner opt-in, per-message binding across separate same-mailbox requests, wrong-mailbox proof, expired/reused links, recovery isolation, session invalidation before failed password changes, provider acceptance counters, rate bounds and direct RPC denial. Interleaved tests hold the provider password request open while the actual owner account API attempts promotion or suspension. Another regression verifies that an unrelated active account's existing session survives a mismatched proof. SQL installation is repeated to check idempotence.

`tests/customer-auth-workspace.test.mjs` exercises the actual form event handlers in the module DOM fixture: registration fields and country filtering, recovery request, password mismatch, proof consumption, URL stripping, expired-link guidance, five locales, local-owner exclusion, owner revision updates and provider-status wording. These checks do not replace a real browser, physical device or mailbox test.
