# Finance, payroll and precious metals

These three authenticated WOW routes use the existing page shell, theme, direction and five interface languages. The entry points are `modules/finance/workspace.js`, `supabase/functions/wow-cloud/modules/finance.mjs` and `supabase/modules/finance.sql`. Apply the module migration after the base WOW schema. Its only public service entry point is `public.wow_finance_service(text,jsonb)`, callable by the service role. All business relations reside in the private `wow_fin` schema with RLS enabled.

## The books and authorization

- PostgreSQL exact `numeric` values own all postings. Public commands send decimal strings. Cash rounds once to two fractional digits, grams support four, quotes support eight. A troy ounce is exactly 31.1034768 grams in quote conversion. A stored quote records its source, observed time, raw unit and normalized rate. Quotes over three days old are flagged. Manual historic quotes keep their source dates.
- New cash entries have an immutable head and signed legs. WOW Cashboxes receives a corresponding `settings/cashbox-entry/finance/<uuid>` record in the same transaction and sync cursor update. Its amounts exactly reflect the signed legs. Database guards protect these records against generic data writes. Payroll names, attendance and supplier details stay out of this projection.
- Live native cash postings enqueue their owner Web Push event inside the same transaction. Transfers report the debited currency and the amount received in the destination currency. Payroll and metal notices contain only the movement, date, amount and currency. A corrected journal entry produces one update. Replays, historical imports, cutover balances and failed commands produce no extra live alert. The shared dispatcher verifies the owner session again before delivery.
- The finance cash view reads older WOW settings movements and cash payments once. Standalone payments take precedence over the same payment embedded in an invoice snapshot. New finance-origin movements use their private journal source in this view. Generic receipts without usable currency/amount cannot produce a cash posting. Canonical invoice accounts use USD, including historical conversion where available.
- Outbound cash and metal quantities require sufficient current balances. A locked workspace serializes mutations with core sync. Retries with the same UUID command and sanitized values return the previous receipt. A changed command under an existing UUID conflicts. The transaction checks live membership, the verified Auth session, section permissions, tenant-bound references and affected resource versions. Read-only roles cannot post, reverse or restore.
- Monthly payroll uses the configured monthly rate and recorded deductions. Daily contracts accrue per present/late shift, with a half-day worth one half. Hourly contracts accrue recorded shift hours. Piecework accrues recorded quantity times the agreed unit rate. An explicit overtime tariff takes precedence. Otherwise the configured workdays, hours and multiplier determine the nominal hourly overtime for time-based contracts. A cash advance debits cash immediately and reduces the period payable. Excess deductions appear as a shortfall. Currency changes on employees with existing financial history require reconciliation.
- Each private section uses the capabilities `view`, `edit`, `delete`, `print` and `export`. Owner-only archive import, history linking and opening metal entries require verified owner identity. Primary customers, invoices and payments keep their existing section grants. Server membership controls historical reads after changes in permission or session.
- Documents and employee photos use permission-checked private byte storage. JPEG, PNG, WebP and PDF are accepted after signature validation, up to 768 KiB per image, 4 MiB per PDF and 64 MiB of byte storage per workspace. The browser downsizes larger photos before attachment. Transactions can reference five documents. Images are rendered from local blobs and PDFs download. No browser-visible table URL, public bucket or provider credential is needed.

## Legacy data and restore

1. An owner opens **Historical records → Import archive** in each applicable scope and selects the locally supplied export. Both the v6 browser-backup keys and the corresponding `acc_*` table names are recognized. The preview inventories all sixteen families, distinguishes absent tables from empty tables, reports excluded connection/settings fields and checks duplicate source IDs.
2. The import classifies employees, attendance and employee-specific transactions/statements as payroll. Metals, metal transactions and their quotes belong to metals. Remaining records belong to finance. Stable UUIDs incorporate the workspace, source family and typed ID. Repeating an unchanged file is safe. A different payload for the same ID requires review. Legacy record details remain in the owner-only history and appear in subsequent native exports.
3. Link source customers and invoices to existing typed WOW IDs. A person who has a numeric ID and a person who has a text ID with the same characters remain distinguishable. Existing suppliers, boxes, categories and employees can also be linked. **Create from historical record** opens a prefilled form for a supplier, category, employee or cashbox, with an explicit currency and opening date, then creates the resource and link atomically.
4. Reconcile each source cash/metal ending balance and select a cutover date before posting its opening. Older transaction/attendance rows are preserved as historical evidence. Importing them does not post a second expense, pay an employee, create a customer or issue another invoice. An owner may establish an opening metal quantity separately with a reference. The source's embedded public URLs remain text in the archive. Authorized media bytes must be acquired separately to create private attachments.
5. A native `wow.finance.v1` export is an ordered command archive with a fixed high-water mark. **Export all accounting** captures all three scopes in their original commit order for full replay, including cross-scope dependencies. Preview executes the actual rules and rolls them back. Apply runs the commands in one database transaction. Large archives stage up to 400 commands per chunk and 128 MiB/100,000 commands per import with a 24-hour expiry. A changed tenant, missing referenced canonical record, insufficient balance, missing cross-scope FX/box, duplicate or mismatched verification stops the import. Restore the required canonical records and finance reference data before dependent payroll and metals. Imported third-party quotes retain their origin and carry imported provenance.
6. The source accounting browser exporter omits some table families including metal quote history, statements and settings. A record count for an absent family is evidence about the file only. The original source also imposed several retrieval limits. Obtain a full authorized table and media export for production reconciliation.

## Offline and verification boundaries

Read responses expose server/device origin and timestamp when the shared transport supplies them. A queued write has a distinct pending status. It has no effect on rendered posted balances until an authoritative receipt arrives. A form retains its data and operation UUID across a failed submission. Attachments, live quote acquisition and restore are online operations.

The live quote adapter is enabled only when the server receives a verified `quoteProvider({base,counter})` dependency. Its observation includes decimal `raw`, UTC `at`, `source` and `unit` (`currency`, `gram` or `troy_ounce`). Without this dependency the live command returns `QUOTE_UNAVAILABLE`. Manual rates and historical observations continue to work. No production provider was configured or contacted during local implementation.

Run from the repository root:

```sh
node --test tests/finance-services.test.mjs tests/finance-workspace.test.mjs tests/finance-push.test.mjs
```

The tests execute the additive migration twice, then execute real PostgreSQL transactions in an in-memory PGlite provider fixture. They also exercise registered UI controls, language updates, cash formatting, role and session boundaries, typed ID migration, pending receipts, replay, compensation, cash/holding conservation, partial pay, frozen periods and atomic bulk rollback. PGlite is single-session. Concurrent production requests, actual browser print/mobile output, multi-device offline sync, provider quotas, live quotations and legacy data counts each require observation in an authorized environment.
